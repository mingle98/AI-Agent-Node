# 调试问题处理手册（当前实现适配版）

本文用于帮助 Agent 在“报错 / 异常 / 故障 / 运行失败”类场景下，给出更稳定、更工程化的排查回复。

目标不是假装已经定位根因，而是：
- 先把问题分类
- 再给出最小必要排查路径
- 少空泛建议
- 少误导式结论

---

## 1. 当前项目中的调试相关能力

当前项目直接相关的能力包括：

- `debug_assistant`
- `analyze_code`
- `code_review`
- `code_explanation`
- 文件读取/按行读取能力（适合看日志、配置、代码片段）

这意味着当前项目适合做的是：
- 错误信息归类
- 日志与堆栈阅读
- 代码片段定位性分析
- 提供排查顺序和修复建议

不应夸大为：
- 自动拿到完整运行态上下文
- 自动复现所有问题
- 自动确认唯一根因
- 自动完成生产环境诊断

---

## 2. 调试的总原则

收到错误反馈时，优先遵循：

1. **先确认现象**，不要先下结论
2. **先看报错文本 / 堆栈 / 复现步骤**
3. **先缩小范围**，再谈修复
4. **先区分环境问题和代码问题**
5. **先给最小排查路径**，不要一次性铺太多建议

---

## 3. 调试问题分类 SOP

收到问题后，优先分成以下几类：

1. **语法/编译类错误**
2. **运行时异常**
3. **依赖/环境问题**
4. **异步/时序问题**
5. **数据/输入问题**
6. **逻辑结果不符合预期**
7. **性能/卡顿/超时问题**

先分类，再决定排查路径。

---

## 4. 各类问题的推荐排查方式

## 4.1 语法 / 编译类错误
常见表现：
- SyntaxError
- 编译失败
- 构建报错
- import / export 错误
- 类型声明错误

推荐先看：
1. 报错行号
2. 报错文件
3. 最近改动
4. 括号、引号、逗号、缩进、导入路径

推荐回复风格：
- 明确指出优先看哪一行附近
- 先让用户贴报错片段和对应代码
- 不要直接给大面积重构建议

---

## 4.2 运行时异常
常见表现：
- TypeError
- Cannot read property of undefined
- null 引用
- index 越界
- key 不存在

推荐先看：
1. 出错堆栈
2. 出错点输入数据
3. 变量是否为空/未定义
4. 上游函数返回值

推荐思路：
- 先确认“哪一个值不符合预期”
- 再追溯是传参问题、默认值缺失，还是分支没覆盖

不要直接假设：
- 一定是类型问题
- 一定是框架 bug

---

## 4.3 依赖 / 环境问题
常见表现：
- 模块找不到
- 版本不兼容
- 命令不存在
- 环境变量缺失
- 本地能跑、线上不能跑

推荐先看：
1. 运行环境（Node / Python / OS）
2. 依赖版本
3. 锁文件是否一致
4. 环境变量
5. 启动命令和工作目录

推荐回答重点：
- 帮用户区分“代码问题”还是“环境问题”
- 列最小检查项

---

## 4.4 异步 / 时序问题
常见表现：
- 数据还没回来就使用
- 状态没更新就读取
- Promise 未等待
- 回调顺序异常

推荐先看：
1. 是否漏了 `await`
2. 是否混用了回调和 Promise
3. 是否在异步完成前访问结果
4. 是否存在竞态条件

推荐回答重点：
- 先把执行顺序讲清楚
- 再指出可能的等待点/竞态点

---

## 4.5 数据 / 输入问题
常见表现：
- 接口返回结构变化
- 字段缺失
- 类型不匹配
- 空数组/空对象
- 文件内容格式不符合预期

推荐先看：
1. 实际输入样例
2. 接口返回样例
3. 边界输入
4. 是否做了空值保护

推荐回答重点：
- 要求用户给最小输入样例
- 先验证数据结构，再谈代码改法

---

## 4.6 逻辑结果不符合预期
常见表现：
- 不报错，但结果错
- 分支走错
- 统计值不对
- UI 显示不符合预期

推荐先看：
1. 预期结果是什么
2. 实际结果是什么
3. 最小复现输入
4. 中间变量值

推荐回答重点：
- 先定义“错在哪里”
- 没有预期 vs 实际对比时，不要假装已经知道逻辑 bug

---

## 4.7 性能 / 卡顿 / 超时问题
常见表现：
- 响应慢
- CPU 飙高
- 页面卡顿
- 脚本执行超时

推荐先看：
1. 是否有大循环/重复计算
2. 是否有不必要的 IO / 网络 / 解析
3. 是否有大文件或大数据量
4. 是否存在死循环 / 重试风暴

推荐回答重点：
- 先识别热点路径
- 先找最明显的高成本操作
- 不要一上来就泛泛谈“优化架构”

---

## 5. 调试时必须先追问的信息

如果用户信息不足，应优先追问这些最小必要信息：

### 5.1 错误文本
- 完整报错信息是什么？

### 5.2 堆栈
- 有完整堆栈的话，最好一起贴出来。

### 5.3 复现步骤
- 这个问题是执行什么操作后出现的？能否给最小复现步骤？

### 5.4 环境信息
- 当前运行环境是什么？例如 Node/Python 版本、框架版本、操作系统。

### 5.5 相关代码片段
- 报错附近的代码片段能贴一下吗？最好包含出错前后几行。

---

## 6. 推荐的调试回复结构

调试类回复建议尽量按这个结构组织：

1. **问题归类**
2. **最可能的 2~3 个方向**
3. **最小检查步骤**
4. **如果要继续排查，需要用户补充什么**
5. **必要时给修复建议**

这样会比“列一堆可能原因”更稳。

---

## 7. 推荐最小排查模板

### 模板 A：用户只给报错一句话
- 从这条报错看，它更像是一个【运行时异常 / 环境问题 / 数据问题】。当前我还不能直接确认唯一根因，但建议你先检查：
  1. 报错堆栈里最上面的业务代码位置
  2. 该位置用到的变量/输入是否为空或结构异常
  3. 最近是否改过依赖、配置或调用顺序
- 如果你把完整堆栈和出错附近代码贴出来，我可以继续帮你缩小范围。

### 模板 B：用户给了代码片段
- 这段代码里我会先重点看：
  1. 输入值来源
  2. 条件分支
  3. 异步顺序 / 空值保护
- 如果你方便，再补一下实际输入样例和预期结果，我可以更准确地判断是不是逻辑问题。

### 模板 C：用户说“就是跑不起来”
- 这类问题我建议先分成两层排查：
  1. 环境层：命令、版本、依赖、环境变量是否正确
  2. 代码层：报错位置、输入数据、调用顺序是否正常
- 你先把启动命令、完整报错和运行环境发我，我能更快帮你定位。

---

## 8. 调试中的高频误区

Agent 在调试场景下不要犯这些错误：

### 8.1 没看堆栈就下根因结论
不应仅凭一句错误文本就说“根因一定是 X”。

### 8.2 过早给大改方案
用户还没定位问题前，不要直接建议重构、换框架、整体改造。

### 8.3 把所有问题都归因于环境
也不要反过来把所有问题都归因为“代码写错了”。

### 8.4 没有输入样例就谈数据 bug
如果没有看到真实输入，不应把数据结构问题说得太确定。

### 8.5 把“可能原因列表”当诊断结果
列可能性可以，但必须告诉用户优先检查顺序。

---

## 9. 不应误导的表述

以下说法不要轻易出现：

- “根因已经确定，就是这个”
- “一定是依赖版本问题”
- “一定是框架 bug”
- “你把这块全部重写就好了”
- “不用看堆栈，我已经知道原因”

---

## 10. 一句话结论

当前项目里，调试类问题最稳的处理方式是：

**先分类、再缩范围、再给最小排查路径；没有堆栈、代码片段和输入样例时，不要假装已经定位根因。**
