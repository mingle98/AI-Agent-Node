# 代码审查检查清单（当前实现适配版）

本文用于帮助 Agent 在代码审查场景下，给出更稳定、更工程化、更像真正 review 的输出。

目标不是装作已经完整理解整个项目，而是：
- 审查结构更稳定
- 重点更清晰
- 少空泛建议
- 少无关“最佳实践”轰炸

---

## 1. 当前代码审查能力定位

当前项目中的代码审查相关能力主要包括：
- `code_review`
- `analyze_code`
- `code_explanation`
- 文件读取/按行读取（适合看代码上下文）

因此更适合做的是：
- 片段级 review
- 单文件 review
- 某一重点维度 review
- 快速识别高风险点与改进方向

不应夸大为：
- 已完整理解整个系统架构
- 已跑过测试并验证所有行为
- 已确认所有结论都是事实问题

---

## 2. 代码审查总原则

进行代码审查时，优先遵循：

1. **先理解目标，再审问题**
2. **先找高风险问题，再谈风格**
3. **先给具体问题，再给抽象建议**
4. **尽量基于代码事实，不基于猜测**
5. **避免把个人偏好说成必改项**

---

## 3. 推荐审查顺序

代码审查建议按下面顺序看：

1. 正确性
2. 安全性
3. 稳定性 / 错误处理
4. 性能
5. 可维护性
6. 可读性 / 风格

这意味着：
- 不要在有明显 bug 风险时先纠结命名风格
- 不要在有安全问题时先讨论 prettier/eslint

---

## 4. 代码审查维度清单

## 4.1 正确性
重点看：
- 逻辑是否可能出错
- 条件分支是否完整
- 边界值是否覆盖
- 返回值 / 状态更新是否一致
- 异步流程是否正确等待

典型问题：
- 漏判空
- 分支遗漏
- 变量来源不稳定
- Promise 未等待
- 假设输入一定符合格式

---

## 4.2 安全性
重点看：
- 是否存在注入风险
- 是否直接信任外部输入
- 是否暴露敏感信息
- 是否有路径、文件、命令执行风险
- 是否缺少必要边界校验

典型问题：
- 硬编码密钥
- 未校验路径
- 未过滤输入
- 直接拼接命令或查询

注意：
- 只有涉及系统边界（用户输入、外部接口、文件路径、网络请求）时，安全审查权重最高

---

## 4.3 稳定性 / 错误处理
重点看：
- 异常路径是否考虑
- 失败时返回是否清晰
- 是否有必要的兜底
- 是否把不能发生的场景过度复杂化

注意：
- 不要为了“显得稳”而硬加大量不必要防御代码
- 只在系统边界和真实可能失败的地方强调错误处理

---

## 4.4 性能
重点看：
- 是否有明显重复计算
- 是否有不必要的循环或扫描
- 是否有大对象重复构建
- IO / 网络 / 文件操作是否过重

典型问题：
- 循环内重复做高成本操作
- 大量无必要 JSON stringify/parse
- 可以局部读取却整文件读取

注意：
- 没有明确热点时，不要空泛谈“性能优化”

---

## 4.5 可维护性
重点看：
- 职责是否清晰
- 是否有重复逻辑
- 命名是否表达真实意图
- 模块边界是否自然
- 是否为了一个小需求引入过度抽象

典型问题：
- 一个函数承担太多事
- 一次性逻辑被过度抽象
- 多处重复而未收敛
- 命名模糊导致难懂

---

## 4.6 可读性 / 风格
重点看：
- 命名清晰度
- 结构清晰度
- 注释是否必要且准确
- 缩进与排版是否一致

注意：
- 风格问题优先级通常低于 bug / 安全 / 稳定性
- 不要把个人偏好的代码写法说成严重问题

---

## 5. 审查重点模式

当前项目 `code_review` 支持这些重点：
- `all`
- `security`
- `performance`
- `style`

因此知识库里建议 Agent 按用户目标调整输出重心。

### 用户要求 `security`
优先看：
- 输入边界
- 路径/命令/注入风险
- 敏感信息
- 权限与暴露面

### 用户要求 `performance`
优先看：
- 热点操作
- 扫描/循环/IO
- 大对象复制
- 同步阻塞

### 用户要求 `style`
优先看：
- 命名
- 结构
- 可读性
- 注释与一致性

### 用户要求 `all`
优先顺序仍应是：
正确性 > 安全性 > 稳定性 > 性能 > 可维护性 > 风格

---

## 6. 推荐代码审查输出结构

建议审查回复尽量按以下结构组织：

1. **总体判断**
2. **高优先级问题**
3. **中低优先级建议**
4. **可选优化项**
5. **如需继续 review，需要的上下文**

这样会比“罗列十几条建议”更有工程感。

---

## 7. 问题分级建议

### P0 / 严重问题
- 明显 bug
- 安全问题
- 会导致数据错乱/服务失败

### P1 / 重要问题
- 高概率异常
- 错误处理缺失
- 明显性能热点
- 维护成本很高的设计缺陷

### P2 / 一般建议
- 结构可优化
- 可读性提升
- 命名与组织改进

### P3 / 可选建议
- 风格统一
- 注释优化
- 小幅重构建议

推荐规则：
- 尽量告诉用户哪些是必须改，哪些只是建议

---

## 8. 推荐审查模板

### 模板 A：快速单文件 review
- 这段代码整体思路是清晰的，但我会优先关注以下几点：
  1. 高优先级问题
  2. 可能导致异常或误行为的分支
  3. 结构和可维护性改进点
- 如果你愿意，我还可以继续结合调用方/输入样例再做一轮更准确的 review。

### 模板 B：安全重点 review
- 从安全角度看，我会重点检查：
  1. 外部输入是否被直接信任
  2. 是否存在路径/命令/注入风险
  3. 是否暴露敏感信息
- 当前最值得优先确认的是这些边界点，而不是先讨论代码风格。

### 模板 C：性能重点 review
- 从性能角度看，我会优先看：
  1. 有没有重复高成本操作
  2. 是否存在不必要的全量扫描/整文件读取
  3. 是否有明显的同步阻塞或大对象重复构建
- 如果你能提供数据规模或调用频率，我可以更准确判断这些点是不是实际瓶颈。

---

## 9. 代码审查中的高频误区

### 9.1 没理解上下文就下结论
没有调用方、输入样例、运行场景时，不要把“猜测风险”说成“已确认 bug”。

### 9.2 风格压过事实问题
有明显 bug 风险时，不要把命名或注释放在前面。

### 9.3 给太多泛化建议
例如：
- 建议重构
- 建议加测试
- 建议上 TypeScript

这些可以提，但不要代替对当前代码的具体判断。

### 9.4 过度工程化
不要因为一个小片段就建议引入复杂抽象、额外层级或通用框架。

### 9.5 把个人偏好包装成最佳实践
例如某种命名风格、某种写法偏好，不应直接上升为必须修改项。

---

## 10. 不应误导的表述

以下说法不要轻易出现：

- “这个一定会出 bug”
- “这里绝对存在安全漏洞”
- “必须重构成 XXX 架构”
- “这段代码完全不可维护”
- “我已经看出整个系统的问题了”

更稳的说法应是：
- “这里存在风险”
- “在某些输入/场景下可能出问题”
- “如果调用方式是 X，这里会更值得优先修复”

---

## 11. 继续审查前建议补充的信息

如果要做更准确的 code review，优先补这些：

- 这段代码的用途
- 输入输出样例
- 调用方上下文
- 数据规模 / 频率
- 是否有报错或实际问题现象

---

## 12. 一句话结论

当前项目里，代码审查最稳的方式是：

**先按正确性、安全性、稳定性、性能、可维护性、风格的顺序审查；优先指出基于代码事实的高风险问题，再补充分层次改进建议。**
